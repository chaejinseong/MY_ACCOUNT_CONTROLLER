# 통합 계정관리 프로그램 기획서

- **작성일**: 2026-09-08
- **작성자**: 명익
- **문서 버전**: v0.5 (후보 메일 계정 정보 직접 저장, 중요 메일 알림을 계정별 요약으로 단순화)
- **프로젝트명(가칭)**: MyVault (변경 가능)

---

## 1. 개요 및 목적

여러 사이트/앱에 흩어져 있는 계정 정보(아이디, 비밀번호, 소속 사이트/앱)를 한 곳에서 안전하게 등록·관리하고, 다수의 Gmail 계정에 쌓이는 메일을 자동으로 정리해주는 개인용 웹 애플리케이션을 만든다. 별도의 회사나 다른 사용자를 위한 서비스가 아니라 본인이 직접 개발해서 본인이 쓰는 것을 전제로 하며, 그만큼 기능은 "내가 실제로 매일 쓸 만한가"를 기준으로 최소한으로 시작해서 점진적으로 확장한다.

핵심 문제의식은 두 가지다.

1. 계정이 너무 많아 비밀번호를 안전하게, 그러나 찾기 쉽게 보관할 방법이 필요하다.
2. 여러 Gmail 계정에 쌓이는 메일 중 상당수는 정기적으로 지우거나 스팸 처리해도 되는데, 매번 손으로 정리하기 귀찮고, 정작 중요한 메일은 묻혀서 놓치기 쉽다.

## 2. 사용자 및 사용 시나리오

- 사용자는 본인 1인이며, 다중 사용자/공유 기능은 1차 범위에서 제외한다.
- 플랫폼은 **웹 앱**을 기준으로 한다. PC 브라우저에서 접속해서 쓰는 것을 기본으로 하되, 반응형으로 만들어 모바일 브라우저에서도 볼 수 있게 한다. (네이티브 모바일 앱/브라우저 확장은 이후 확장 과제로 남긴다.)

**대표 시나리오**

- "Google 계정으로 앱에 로그인한다 → 등록된 기기라면 지문/Face ID로 바로, 처음 쓰는 기기라면 마스터 비밀번호로 잠금을 해제한다."
- "새로 가입한 사이트가 있다 → 사이트/앱 이름, URL, 아이디, 비밀번호를 등록한다."
- "예전에 등록해둔 어떤 사이트 비밀번호가 기억나지 않는다 → 검색해서 찾아보고, 마스터 비밀번호로 잠금 해제 후 확인/복사한다."
- "아침에 일어나서 프로그램을 켠다 → 지난 하루 동안 자동으로 걸러진 메일 후보 목록(삭제 대상/스팸 대상)을 훑어보고 일괄 승인한다 → 승인된 메일은 실제 Gmail에서 삭제/스팸 처리된다."
- "키워드 규칙에 걸린 메일 중 '중요' 표시가 붙은 것은 별도 알림으로 바로 확인한다."

## 3. 핵심 기능 정의

### 3.1 사이트 및 앱 등록

- 사이트/앱 단위로 항목을 등록한다. 등록 항목 예시: 서비스명, 서비스 URL 또는 앱 이름, 카테고리(예: 금융/쇼핑/SNS/업무/기타), 아이콘(파비콘 자동 수집 또는 직접 업로드), 메모.
- 카테고리/태그 기준으로 목록을 분류하고 검색할 수 있어야 한다.
- 하나의 사이트에 여러 계정(부계정)을 등록할 수 있어야 한다 (예: 같은 쇼핑몰에 개인용/부모님용 계정).

### 3.2 계정 및 비밀번호 등록

- 등록된 사이트/앱마다 아이디(또는 이메일), 비밀번호, 추가 인증 정보(2단계 인증용 백업코드, 보안질문 등, 선택 입력)를 저장한다.
- 비밀번호는 평소 목록 화면에서는 마스킹(`••••••••`) 처리하고, 클릭 시에만 마스터 비밀번호 재확인 없이(세션 내에서는) 보거나 복사할 수 있게 한다. 단, 일정 시간 idle 상태거나 앱을 재접속하면 다시 잠금(마스터 비밀번호 재입력) 상태로 돌아간다.
- 간단한 비밀번호 생성기(길이/문자 조합 옵션)를 함께 제공해 새 계정 등록 시 바로 안전한 비밀번호를 만들 수 있게 한다.
- 이미 등록된 비밀번호 중 동일한 비밀번호를 여러 사이트에서 재사용하고 있는 경우 경고 표시(중복 사용 탐지)를 1차 확장 기능으로 고려한다.
- 같은 사이트(URL/앱 이름 기준)에 같은 아이디로 중복 등록하는 것은 막는다. 단, 아이디가 다른 부계정(3.1)은 문제없이 여러 개 등록할 수 있다.

### 3.3 안전한 관리 (보안)

자세한 보안 설계는 7장에서 다루되, 기능 관점에서 필요한 항목은 다음과 같다. 로그인/잠금해제는 두 단계로 나눈다: **① 앱 로그인(신원 확인)** 과 **② 마스터 비밀번호(데이터 열람 자격 확인)**. 이 둘은 서로 독립적으로 유지한다 — 한쪽이 뚫려도 다른 쪽 없이는 데이터가 열리지 않게 하기 위해서다.

- **앱 로그인 = Google 계정 로그인**: 자체 회원가입/비밀번호 시스템을 만들지 않고 Google 로그인(OAuth)으로 신원을 확인한다. 비밀번호 저장·재설정 기능을 직접 구현할 필요가 없다.
- **마스터 비밀번호**: 앱 로그인과 별개로, 저장된 계정 데이터를 실제로 열람하기 위한 두 번째 비밀번호. 모든 계정 데이터의 열람은 마스터 비밀번호로 잠금 해제된 세션 안에서만 가능하다. **Google 계정과 절대 연결하지 않는다** — "구글 이메일로 마스터 비밀번호 재설정" 같은 기능은 만들지 않는다. 그렇게 하면 구글 계정이 뚫렸을 때 마스터 비밀번호까지 우회할 수 있게 되어, 두 단계를 분리한 의미가 없어지기 때문이다.
- **기기별 생체인증 빠른 잠금해제**: 지문/Face ID(또는 노트북의 터치ID/윈도우 헬로) 같은 플랫폼 인증을 지원하는 기기에서는, 그 기기에서 최초 1회 마스터 비밀번호로 잠금을 해제한 뒤 "이 기기에서 생체인증으로 빠르게 열기"를 등록할 수 있다. 이후 그 기기에서는 지문/Face ID만으로 잠금 해제가 가능하다. 단, 이는 마스터 비밀번호를 대체하는 것이 아니라 **이미 신뢰된 기기에 한해 타이핑을 생략해주는 것**이며, 등록되지 않은 새 기기에서는 항상 마스터 비밀번호가 필요하다.
- **자동 잠금**: 일정 시간 미사용 시 자동으로 잠기고, 브라우저 탭을 닫거나 새로고침하면 다시 잠긴다.
- **저장 시 암호화**: 비밀번호 등 민감 정보는 서버/DB에 평문으로 저장하지 않고 암호화된 형태로만 저장한다.
- **활동 로그**: 언제 어떤 계정 정보를 조회/수정했는지 최소한의 로그를 남겨, 이상 접근을 나중에라도 확인할 수 있게 한다.
- **백업/복구**: 마스터 비밀번호를 분실했을 때를 대비한 복구 수단(오프라인으로 보관하는 복구 키/문구)을 설계 단계에서 함께 마련한다. 이 복구 수단 역시 Google 계정과 무관하게 동작해야 한다.

### 3.4 이메일 관리 기능

가장 복잡하고 이 프로그램의 핵심 차별점이 되는 기능이다. 대상은 **Gmail, 다중 계정**으로 한정한다.

**3.4.1 조건 기반 규칙 등록**

- 조건은 아래 5가지 형식 중에서 1개~5개까지 자유롭게 선택해서 하나의 규칙을 만든다.
  1. 발신자 (이메일 주소/도메인)
  2. 제목 키워드
  3. 본문 키워드 (미리보기 텍스트 기준)
  4. 이모티콘 포함 여부 (제목/본문에 이모지 포함, 광고성 메일 판별에 유용)
  5. 첨부파일 유무
- 조건을 2개 이상 선택하면 **모두 만족(AND)** 또는 **하나라도 만족(OR)** 중 하나를 사용자가 골라 결합 방식을 정한다. 조건이 1개뿐이면 이 선택은 필요 없다.
- 선택한 조건(들) + 결합 방식(AND/OR) + 처리 방식(삭제 후보 / 스팸 후보 / 중요 표시)을 묶어 하나의 규칙으로 저장한다.
- 규칙 예시: "발신자가 광고 도메인" **AND** "제목에 '이벤트' 포함" → 삭제 후보 / "제목에 '결제' 포함"(조건 1개) → 중요 표시 / "본문에 이모티콘 포함" **OR** "첨부파일 없음" → 스팸 후보
- 규칙은 계정별로 다르게 설정하거나, 여러 Gmail 계정에 공통 규칙으로 적용할 수 있어야 한다.

**3.4.2 자동 수집 (매일/주기적 스캔)**

- 등록된 Gmail 계정들을 주기적으로(예: 몇 시간 간격) 스캔해서 규칙에 매칭되는 메일을 찾아 "대기함"에 모아둔다. 이 시점에는 실제 Gmail의 메일함은 건드리지 않는다.
- "삭제 후보"와 "스팸 후보"는 별도 리스트로 모아 매일 아침 검토 화면에 노출한다.

**3.4.3 매일 아침 승인 플로우**

- 아침에 접속하면 지난 주기 동안 쌓인 후보 메일 목록(발신자/제목/규칙에 매칭된 이유)을 한 화면에서 보여준다.
- 사용자는 목록을 훑어보고 "전체 승인", "개별 선택 승인/제외" 중 선택해 실제로 Gmail에서 삭제하거나 스팸 처리하도록 확정한다.
- 승인 전 후보 목록에서 실수로 지우면 안 되는 메일은 제외하거나, 규칙 자체를 그 자리에서 수정할 수 있게 한다.
- 승인 이력은 남겨서 나중에 "이 규칙 때문에 계속 잘못 걸리네" 같은 패턴을 찾아 규칙을 다듬을 수 있게 한다.

**3.4.4 중요 메일 알림**

- "중요" 규칙에 매칭된 메일은 삭제/스팸 대기함이 아니라 별도로 관리한다. 지금 단계에서는 별도 알림 채널(푸시 등)을 만들지 않고, **대시보드에 "마지막으로 확인한 이후 쌓인 중요 메일 개수를 계정별로 묶어서" 요약**해 보여주는 정도로 단순하게 시작한다 (예: "중요 메일 5건 — A계정 3건, B계정 2건"). 요약을 클릭하면 실제 목록(중요 메일함)으로 이동한다.
- 중요 메일은 자동 처리 대상에서 완전히 제외되어, 실수로 삭제/스팸 처리될 위험이 없어야 한다.
- 푸시/이메일/메신저 알림처럼 실제로 알림을 "보내는" 채널은 나중에 필요해지면 추가한다(9.3).

**참고 및 제약사항**: 카카오메일/카카오톡 메시지 자동 관리는 이번 범위에서 제외한다. 카카오톡 개인 대화 내용은 카카오의 정책상 외부 프로그램이 자동으로 읽거나 처리할 수 있는 공식 API가 없어, 계정 자체(로그인 정보) 등록·관리 대상으로만 다루고 메시지 자동화는 다루지 않는다.

## 4. 시스템 구성 개요 (웹 앱 기준)

| 영역 | 내용 |
|---|---|
| 프론트엔드 | 웹 브라우저에서 접속하는 반응형 웹 앱 |
| 백엔드 | 계정/비밀번호 데이터 처리, 암호화/복호화, Gmail API 연동, 스케줄링(주기적 메일 스캔) 담당 서버 |
| 데이터베이스 | 계정 정보, 암호화된 비밀번호, 이메일 규칙, 메일 후보 목록, 로그 저장 |
| 외부 연동 | Gmail API (OAuth 2.0 인증, 메일 검색·라벨링·삭제·스팸 처리 권한) |
| 인증 | 앱 자체 로그인 + 마스터 비밀번호 별도 이중 구조 |

세부 기술 스택(언어/프레임워크/DB 종류/호스팅 위치 등)은 이후 기술 검토 단계에서 별도로 정한다. 다만 백엔드는 프론트엔드와 분리된 **API 서버 형태**로 설계해서, 지금은 웹 앱 하나만 쓰더라도 나중에 모바일 앱이나 브라우저 확장 같은 다른 클라이언트가 생기면 같은 API를 그대로 재사용할 수 있게 한다. (9장 참고)

## 5. 주요 화면 구성 (초안)

1. **로그인 / 마스터 비밀번호 입력 화면** — 앱 계정 로그인 후 마스터 비밀번호로 한 번 더 잠금 해제.
2. **대시보드** — 등록된 계정 수, 오늘 처리 대기 중인 메일 후보 수, 중요 메일 알림 요약을 한눈에 보여주는 첫 화면.
3. **계정 목록 화면** — 카테고리/태그별 필터, 검색, 사이트별 계정 카드/리스트.
4. **계정 상세/등록·수정 화면** — 사이트 정보, 아이디/비밀번호, 메모, 비밀번호 생성기 포함.
5. **메일 관리 - 규칙 설정 화면** — Gmail 계정 연결 관리, 키워드/발신자 규칙 등록·수정·삭제.
6. **메일 관리 - 오늘의 검토함** — 삭제 후보/스팸 후보 리스트, 개별·전체 승인 UI.
7. **중요 메일 알림함** — 중요로 분류된 메일 목록.
8. **설정 화면** — 마스터 비밀번호 변경, 자동 잠금 시간 설정, Gmail 계정 연결/해제, 백업/복구.

## 6. 데이터 모델 개요 (초안)

- **Account (계정)**: id, 서비스명, URL/앱명, 카테고리, 아이디, 암호화된 비밀번호, 메모, 생성일, 수정일
- **EmailAccount (연결된 메일 계정)**: id, **provider_type**(현재는 `gmail`만 존재, 값 추가만으로 다른 메일 서비스 지원), 인증 토큰(암호화), 표시 이름, 활성 여부 — Gmail 하나만 있는 지금도 별도 엔티티로 분리해두어, 나중에 다른 메일 provider가 추가돼도 EmailRule·EmailCandidate 구조를 바꿀 필요가 없게 한다.
- **EmailRule (메일 규칙)**: id, 연결된 EmailAccount, **logical_operator**(조건이 2개 이상일 때 AND/OR 중 무엇으로 판정할지), 처리 유형(삭제/스팸/중요 — 값 추가로 새 처리 유형 확장 가능), 활성 여부
- **EmailRuleCondition (규칙 조건)**: id, 연결된 EmailRule, **condition_type**(발신자/제목 키워드/본문 키워드/이모티콘 포함 여부/첨부파일 유무 — 값 추가로 조건 종류 계속 확장 가능), 조건 값 — 규칙 하나에 1~5개까지 연결 가능
- **EmailCandidate (메일 후보)**: id, 매칭된 규칙, **연결된 EmailAccount(어느 계정에서 온 메일인지 직접 저장)**, 메일 메타정보(발신자/제목/수신일), 상태(대기/승인됨/제외됨), 처리일시 — 규칙을 거치지 않고도 바로 어느 계정 메일인지 알 수 있어 계정별 요약(3.4.4)을 빠르게 만들 수 있고, 나중에 규칙이 삭제/변경돼도 "그때 어느 계정 메일을 처리했는지" 기록이 그대로 남는다.
- **NotificationChannel (알림 채널)**: id, **channel_type**(현재는 `in_app`만, 값 추가로 푸시·이메일·슬랙 등 확장), 설정값, 활성 여부 — 지금 단계에서는 후보 메일 하나하나와 직접 연결하지 않고, "지금 어떤 알림 방법이 켜져 있는지"를 나타내는 설정 목록으로만 둔다. 여러 채널로 실제 발송을 추적할 필요가 생기면 그때 별도 발송 기록 테이블을 추가한다(9.3).
- **ActivityLog (활동 로그)**: id, 대상(Account/EmailRule 등), 행위 유형(조회/수정/삭제/승인), 발생 시각

이렇게 서비스 종류·조건 종류·알림 채널을 전부 하드코딩된 컬럼이 아니라 "타입 값 + 공통 구조"로 설계해두면, 새 기능이 추가될 때마다 테이블 구조를 바꾸지 않고 값과 처리 로직만 추가하면 된다.

## 7. 보안 및 개인정보 고려사항

- 비밀번호 등 민감 데이터는 **AES-256 등 강력한 대칭키 암호화**로 저장하고, 암호화 키는 마스터 비밀번호에서 파생(예: PBKDF2/Argon2 등 키 유도 함수 사용)시켜 서버에 평문 마스터 비밀번호나 원본 키를 저장하지 않는 구조를 목표로 한다.
- Gmail 연동은 **OAuth 2.0**을 사용해 비밀번호를 직접 저장하지 않고, 필요한 최소 권한(스코프)만 요청한다 (예: 메일 읽기/라벨·삭제/스팸 처리에 필요한 범위로 한정, 계정 전체 접근 금지).
- 발급받은 Gmail OAuth 토큰은 access token과 refresh token을 각각 별도로 암호화해서 저장한다 — 몇 시간마다 갱신되는 access token만 복호화/재암호화하면 되고, 더 오래 쓰이는 민감한 refresh token은 갱신 때마다 불필요하게 노출되지 않는다.
- 웹 앱 특성상 통신 구간은 HTTPS로만 서비스하고, 세션은 idle timeout을 두어 자동 잠금한다.
- 1인 사용 목적이라도 외부에서 접근 가능한 서버에 올릴 경우를 대비해 로그인 시도 제한(brute-force 방지), 2단계 인증(선택) 도입을 고려한다.
- 마스터 비밀번호 분실 시 복구 수단이 없으면 모든 데이터에 영구히 접근할 수 없게 되므로, 오프라인 복구 키/복구 문구(recovery phrase) 발급 방식을 설계 단계에서 반드시 정한다.

## 8. 개발 로드맵 (제안)

**Phase 1 — MVP (계정/비밀번호 관리)**
- 마스터 비밀번호 기반 로그인/잠금
- 사이트/앱 등록, 계정(아이디/비밀번호) 등록·조회·수정·삭제
- 비밀번호 암호화 저장, 목록 검색/카테고리 필터
- 비밀번호 생성기

**Phase 2 — Gmail 연동 기본**
- Gmail OAuth 연동 (다중 계정 연결)
- 키워드/발신자 기반 규칙 등록
- 주기적 스캔 → 대기함 적재

**Phase 3 — 승인 플로우 및 알림**
- 매일 아침 검토 화면, 전체/개별 승인 → 실제 Gmail 삭제/스팸 처리 연동
- 중요 메일 알림함
- 승인 이력 기반 규칙 개선 힌트

**Phase 4 — 확장 (선택)**
- 비밀번호 재사용 탐지, 2단계 인증 도입
- 모바일 최적화 / PWA
- 브라우저 확장 연동(자동 입력)
- 카카오 계정(로그인 정보) 관리 범위 확대 검토

## 9. 확장 가능한 구조 설계 (Extensibility)

지금은 "웹 앱 + Gmail만" 범위로 시작하지만, 나중에 다른 메일 서비스·다른 플랫폼·새로운 인증 방식이 추가될 수 있다는 것을 전제로 처음부터 아래 원칙을 지켜서 설계한다. 목표는 "새 기능을 추가할 때 기존 코드를 뜯어고치지 않고, 새 모듈만 얹을 수 있는 구조"다.

### 9.1 메일 관리 — Provider 플러그인 구조

- 메일 관리 로직을 "규칙 엔진 / 승인 플로우 / 알림"이라는 **공통 코어**와, "Gmail에서 메일을 읽고 삭제·스팸 처리하는 방법"을 담당하는 **Provider 모듈**로 분리한다.
- Provider는 최소한 "메일 목록 가져오기, 라벨/스팸 처리하기, 삭제하기" 같은 공통 인터페이스만 지키면 되고, 코어 로직(규칙 매칭, 대기함 적재, 아침 승인 화면)은 어떤 Provider든 그대로 재사용한다.
- 향후 카카오메일·네이버메일·Outlook 등을 추가하고 싶어지면, 6장의 EmailAccount에 `provider_type` 값 하나를 추가하고 해당 Provider 모듈만 새로 구현하면 된다.

### 9.2 규칙 엔진의 확장성

- 규칙은 처음부터 발신자/제목 키워드/본문 키워드/이모티콘 포함 여부/첨부파일 유무 5가지 조건을 1~5개까지 AND/OR로 조합할 수 있는 구조로 시작한다(3.4.1). 더 확장하고 싶어지면 EmailRuleCondition의 `condition_type`에 정규식, 메일 크기, 수신 빈도 같은 새 값만 추가하면 된다.
- 규칙의 "판정 방식" 자체도 나중에 단순 키워드 매칭에서 더 똑똑한 분류(예: 과거 승인/제외 이력을 학습해 자동 추천)로 바꿀 수 있도록, 판정 로직을 코어와 분리된 별도 모듈로 둔다.

### 9.3 알림 채널 확장

- "중요 메일 알림"을 인앱 알림 한 가지에 고정하지 않고, 6장의 NotificationChannel처럼 채널을 갈아 끼울 수 있는 구조로 둔다. 이후 푸시 알림, 이메일 알림, 메신저(예: 슬랙/텔레그램) 알림 등을 채널 모듈만 추가해서 확장할 수 있다.

### 9.4 플랫폼/클라이언트 확장

- 백엔드를 프론트엔드와 분리된 API 서버로 두면(4장), 지금의 웹 앱 외에 모바일 앱이나 브라우저 확장을 나중에 추가해도 같은 계정·비밀번호·메일 관리 API를 그대로 재사용할 수 있다.
- 브라우저 확장은 특히 "사이트 방문 시 자동으로 등록된 아이디/비밀번호 자동 입력" 같은 기능과 잘 맞아서, Phase 4 이후 우선 후보로 고려한다.

### 9.5 인증/보안 확장

- 지금은 마스터 비밀번호 하나지만, 인증 로직을 "마스터 비밀번호 검증"이라는 하나의 방식에 묶어두지 않고, 이후 2단계 인증(OTP), 생체인증, WebAuthn/보안키 같은 인증 수단을 나란히 추가할 수 있는 구조(인증 방식 목록에 항목 추가)로 둔다.

### 9.6 계정 관리 — 커스텀 필드/카테고리 확장

- 3.1의 카테고리를 고정 목록이 아니라 사용자가 직접 추가·수정할 수 있게 하고, 계정(Account) 항목에도 사이트별로 다른 부가 정보(예: 보안질문, 유효기간, 소속 그룹)를 자유롭게 추가할 수 있는 커스텀 필드 구조를 열어둔다. 카카오 계정처럼 이후 관리 대상이 늘어나도 스키마를 바꾸지 않고 대응할 수 있다.

### 9.7 기능 플래그

- 확장 기능(2단계 인증, 새 메일 Provider, 새 알림 채널 등)은 설정에서 켜고 끌 수 있는 기능 플래그 형태로 두어, 완성되지 않은 확장 기능이 기존 핵심 기능(계정/비밀번호 관리)에 영향을 주지 않게 하고 점진적으로 릴리즈한다.

## 10. 리스크 및 제약사항

- Gmail API의 삭제/스팸 처리 권한은 민감한 권한이라 Google의 OAuth 심사(앱이 일정 사용자 수를 넘기지 않는 개인용이라면 "테스트 사용자" 등록으로 우회 가능하나, 이 경우 사용 가능한 테스트 계정 수 제한이 있을 수 있음)를 확인해야 한다.
- 자동 스캔 주기와 API 호출 한도(Gmail API quota)를 고려해 스캔 빈도를 설계해야 한다.
- 규칙이 정교하지 않으면 오탐(중요 메일이 삭제 후보로 분류)이 발생할 수 있어, 승인 단계를 절대 생략하지 않는 것을 원칙으로 한다.
- 카카오톡 메시지 자동 처리는 공식적으로 불가능하므로 기획 범위에서 명시적으로 제외한다.
- 1인 개발 프로젝트이므로 일정은 여유 있게 잡고, Phase 1(계정/비밀번호 관리)만으로도 완결된 결과물이 되도록 우선순위를 둔다.
